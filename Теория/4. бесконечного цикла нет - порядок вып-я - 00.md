## Нет никакого бесконечного цикла

Тут путаница из-за слова `TRIGGER`. Давай разберём.

### Что делает функция

```sql
CREATE OR REPLACE FUNCTION fnc_trg_person_insert_audit()
RETURNS TRIGGER AS ...
```

Функция **не вызывает триггер** и **не возвращает триггер**. `RETURNS TRIGGER` — это просто **метка-допуск**, которая говорит PostgreSQL: «эту функцию разрешено подключать к триггерам». Функция сама по себе ничего не запускает — она **ждёт**, пока её вызовут.

### Что делает триггер

```sql
CREATE TRIGGER trg_person_insert_audit
AFTER INSERT ON person
FOR EACH ROW
EXECUTE FUNCTION fnc_trg_person_insert_audit();
```

Триггер — это **правило-наблюдатель**, прибитое к таблице `person`. Он говорит: «Когда кто-то сделает INSERT в `person`, вызови функцию `fnc_trg_person_insert_audit()`».

### Кто кого вызывает

Цепочка **однонаправленная**, никакого цикла:

```
Ты делаешь INSERT в person
        ↓
PostgreSQL видит: на person висит триггер
        ↓
Триггер вызывает функцию fnc_trg_person_insert_audit()
        ↓
Функция делает INSERT в person_audit
        ↓
Всё. Конец.
```

Функция вставляет данные в `person_audit`, а **не** в `person`. На таблице `person_audit` никакого триггера нет — поэтому цепочка обрывается. Цикл возник бы только если бы функция делала INSERT обратно в `person` — но она этого не делает.

## Порядок работы всего скрипта

```
1. DELETE FROM person WHERE id = 10;
   → Удаляем Дамира из person (если он там есть от прошлого запуска)

2. DROP TABLE IF EXISTS person_audit;
   → Удаляем старую таблицу аудита (если есть)

3. CREATE TABLE person_audit (...);
   → Создаём чистую таблицу аудита

4. CREATE OR REPLACE FUNCTION fnc_trg_person_insert_audit() ...
   → Регистрируем функцию в каталоге базы. Она просто лежит и ждёт.

5. DROP TRIGGER IF EXISTS trg_person_insert_audit ON person;
   → Удаляем старый триггер (если есть)

6. CREATE TRIGGER trg_person_insert_audit ...
   → Вешаем наблюдателя на таблицу person.
     Теперь любой INSERT в person будет вызывать функцию из шага 4.

7. INSERT INTO person(id, name, age, gender, address)
   VALUES (10, 'Damir', 22, 'male', 'Irkutsk');
   → Вставляем Дамира в person.
   → PostgreSQL видит триггер → вызывает функцию →
     функция вставляет копию Дамира в person_audit.

8. SELECT * FROM person_audit;
   → Проверяем: видим одну строку с данными Дамира и type_event = 'I'.
```

## Что относится к триггеру, а что нет

```sql
-- Это ОПРЕДЕЛЕНИЕ триггера (привязка наблюдателя к таблице):
CREATE TRIGGER trg_person_insert_audit
AFTER INSERT ON person
FOR EACH ROW
EXECUTE FUNCTION fnc_trg_person_insert_audit();

-- Это ОБЫЧНЫЙ INSERT, не часть триггера:
INSERT INTO person(id, name, age, gender, address)
VALUES (10, 'Damir', 22, 'male', 'Irkutsk');

-- Это ОБЫЧНЫЙ SELECT, не часть триггера:
SELECT * FROM person_audit;
```

INSERT и SELECT — это **самостоятельные команды**. Просто INSERT **случайно** затрагивает таблицу `person`, на которой висит триггер, и поэтому триггер срабатывает. Но сам INSERT об этом даже «не знает» — он просто вставляет строку, а триггер работает «за кулисами».

Аналогия: ты открываешь дверь (INSERT). На двери стоит датчик (триггер). Датчик вызывает сирену (функцию). Но ты не «запускаешь сирену» — ты просто открываешь дверь. Сирена — побочный эффект.
