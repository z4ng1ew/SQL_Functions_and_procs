## Почему SQL непроцедурный

### Корень — в философии языка

SQL создан в 1970-х годах в IBM на основе работы Эдгара Кодда (Edgar Codd) — математика, который предложил реляционную модель данных. Ключевая идея была такая:

**Ты описываешь ЧТО хочешь получить, а не КАК это получить.**

Это называется **декларативный подход** (declarative — описательный). Противоположность — **императивный подход** (imperative — приказной), как в Си, где ты пишешь пошаговые инструкции.

### Сравнение на примере

Задача: найти всех мужчин старше 20 лет.

Императивный подход (Си):

```c
// ТЫ командуешь КАК делать — каждый шаг вручную:
for (int i = 0; i < count; i++) {
    if (persons[i].gender == MALE && persons[i].age > 20) {
        printf("%s\n", persons[i].name);
    }
}
```

Декларативный подход (SQL):

```sql
-- ТЫ описываешь ЧТО хочешь — без инструкций как искать:
SELECT name FROM person WHERE gender = 'male' AND age > 20;
```

В SQL нет цикла, нет индекса, нет сравнения на каждой итерации. Ты просто говоришь «дай мне мужчин старше 20» — а **как** искать, решает оптимизатор (query planner — планировщик запросов) внутри PostgreSQL. Он может использовать индекс, полный перебор, параллельное сканирование — что окажется быстрее. Ты этим не управляешь.

### Зачем так сделано

Кодд хотел, чтобы работа с данными была **как математика**, а не как программирование. В математике ты пишешь:

```
M = { x ∈ Person | x.gender = 'male' ∧ x.age > 20 }
```

Это описание множества, а не алгоритм поиска. SQL — это по сути та же запись, только на английском языке.

### Почему появился PL/pgSQL

Чистый SQL мощный, но иногда **недостаточен**. Нельзя написать:

- цикл с условием выхода
- ветвление с побочными эффектами (side effects — когда кроме вычисления результата происходят дополнительные действия, например запись в другую таблицу)
- обработку ошибок с try/catch
- пошаговую логику с промежуточными переменными

Поэтому в PostgreSQL добавили PL/pgSQL — **процедурную надстройку**. Это компромисс: SQL остался декларативным ядром, а PL/pgSQL добавил привычные циклы, переменные, IF/ELSE для случаев, когда декларативного подхода не хватает.

### Итого

```
1970-е: SQL создан как ДЕКЛАРАТИВНЫЙ язык
        «Скажи ЧТО хочешь, я сам разберусь КАК»
                    ↓
Проблема: иногда нужна пошаговая логика
                    ↓
Решение:  PL/pgSQL — процедурная надстройка
          «Ладно, если надо — вот тебе циклы и переменные»
```

SQL «не любит» процедурный код не из-за ограничений компилятора или СУБД, а **by design** (по замыслу) — он изначально задуман как язык описания, а не инструкций. Когда ты пишешь чистый SQL вместо PL/pgSQL, оптимизатор PostgreSQL имеет больше свободы для оптимизации — потому что ты не диктуешь ему КАК делать, а лишь говоришь ЧТО нужно.
